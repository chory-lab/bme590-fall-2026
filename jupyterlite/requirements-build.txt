# Build environment for the JupyterLite site. Install into the short-path venv
# (see README.md for the Windows MAX_PATH note):
#
#   C:\plrlite\venv\Scripts\python.exe -m pip install -r requirements-build.txt
#
# Every version here is pinned, and the pyodide kernel pin is load-bearing.
#
# jupyterlite-core 0.8.1 ships JupyterLab 4.6.0 (@jupyterlab/coreutils 6.6.0,
# @jupyterlab/logconsole 4.6.0). jupyterlite-pyodide-kernel 0.8.2+ is built
# against JupyterLab 4.6.1 and declares `^6.6.1` / `^4.6.1` for those shared
# singletons. The federation runtime then refuses to load the extension:
#
#   [Federation Runtime] Version 6.6.0 ... does not satisfy ... ^6.6.1
#
# It is only a *warning* in the console -- but the plugin never activates, so
# the site registers zero kernelspecs. The Launcher loses its Notebook section,
# every notebook opens to a "Select Kernel" modal whose only option is
# "No Kernel", and nothing can execute. Left unpinned, pip picks 0.8.3 and the
# next rebuild silently ships a site that cannot run a single cell.
#
# There is no jupyterlite-core 0.8.2/0.8.3 on PyPI, so the kernel pins back.
# When upgrading, move BOTH lines together and re-run jupyterlite/drive.cjs,
# which asserts a kernel exists and a cell actually executes.
# The metapackage is what provides `python -m jupyterlite`, which build.py
# invokes. jupyterlite-core alone installs the `jupyter lite` CLI but no
# runnable `jupyterlite` module, and the failure is easy to misread:
#   No module named jupyterlite.__main__; 'jupyterlite' is a package and
#   cannot be directly executed
